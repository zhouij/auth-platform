# Auth Gateway System Implementation Plan (v4)

> Supersedes `2026-05-06_122900-auth-gateway-v3.md`.
> This version keeps the four-service direction from v3, but corrects the auth-server, IAM, gateway, database, Docker, and test contracts that made v3 non-implementable.

## Goal

Build a Kotlin Spring Boot authentication system with four independently deployable services:

- `iam-server`: user lifecycle, Argon2id password hashing, role membership, email-based login, and internal credential validation.
- `auth-server`: OAuth2/OIDC Authorization Server, token issuance, consent, client registry, token persistence, and signing keys.
- `gateway`: Spring Cloud Gateway reverse proxy with JWT validation and optional sanitized claim headers.
- `resource-server`: sample domain service demonstrating scope, role, and owner-based authorization.

All database-backed services use PostgreSQL with Flyway. The gateway remains stateless and has no database.

## Version Policy

Do not use the v3 baseline of Spring Boot 3.2.x and Spring Cloud 2023.0.x for a new implementation.

Use one of these version tracks and keep all versions aligned by BOM:

- Preferred conservative track: Spring Boot 3.5.x, Spring Cloud 2025.0.x, Spring Authorization Server 1.x, Java 17 or 21.
- Boot 4 track: Spring Boot 4.0.x and the matching Spring Cloud Gateway 5.x line only after checking Spring Authorization Server and Spring Security API changes.

Implementation rule: select versions from Spring Initializr or official Spring project compatibility tables at implementation time. Do not mix Spring Boot, Spring Cloud, and Spring Security versions manually.

## Dependency Policy

The project should be Spring Boot dependency-based. Do not depend on low-level Spring Security artifacts directly when a Boot starter exists.

Root build rules:

- Use the Spring Boot Gradle plugin and Boot dependency management for all Spring Framework, Spring Security, Jackson, Hibernate, Flyway, Testcontainers, and Micrometer versions.
- Import the matching Spring Cloud BOM only for Spring Cloud components.
- Define module dependencies through a Gradle version catalog or a small convention plugin so each module cannot silently drift.
- Do not pin versions on dependencies managed by the Boot or Spring Cloud BOM.
- Pin only genuinely external dependencies that are not managed by either BOM.

Expected starter usage:

- Auth server: `spring-boot-starter-web`, `spring-boot-starter-security`, `spring-boot-starter-oauth2-authorization-server`, `spring-boot-starter-jdbc`, `spring-boot-starter-actuator`, Flyway, PostgreSQL.
- Gateway: `spring-boot-starter-webflux`, `spring-boot-starter-security`, `spring-boot-starter-oauth2-resource-server`, `spring-boot-starter-actuator`, Spring Cloud Gateway WebFlux starter.
- IAM server: `spring-boot-starter-web`, `spring-boot-starter-security`, `spring-boot-starter-data-jpa`, `spring-boot-starter-validation`, `spring-boot-starter-actuator`, Flyway, PostgreSQL.
- Resource server: `spring-boot-starter-web`, `spring-boot-starter-security`, `spring-boot-starter-oauth2-resource-server`, `spring-boot-starter-data-jpa`, `spring-boot-starter-validation`, `spring-boot-starter-actuator`, Flyway, PostgreSQL.

## Corrections From v3

1. The auth server must use the full Spring Authorization Server JDBC schema, not a partial hand-written `oauth2_registered_client` table.
2. Client secrets must be present and password-encoded. `{noop}` is allowed only in throwaway local demos.
3. The auth server must define a persistent `JWKSource<SecurityContext>` and a `JwtDecoder` so `/oauth2/jwks`, JWT issuance, and OIDC work.
4. Interactive login must use form login plus a custom `AuthenticationProvider` that validates credentials with IAM. A `UserDetailsService` alone is not enough.
5. IAM must expose a dedicated internal credential validation API. The auth server must not call IAM admin endpoints for login.
6. Docker URLs must use Compose service names for internal calls and a stable external issuer URL for tokens.
7. Gateway route definitions must live in one place. Use YAML routes, not duplicate YAML plus `RouteLocator` code.
8. Public endpoints must be public in both gateway security and the gateway enrichment filter.
9. Resource services must validate JWTs themselves. Gateway claim headers are convenience hints only, not the security authority.
10. Test snippets must be valid Kotlin and must exercise the broken contracts above.

## Migration From Earlier Versions

This v4 design supersedes v1, v2, and v3. If code was started against an earlier plan:

- v1 (monolith): discard and restart from v4. The single-process model conflates gateway and auth server concerns and has no IAM.
- v2 (three-service): extract IAM from the auth server's in-memory user store. Add PostgreSQL + Flyway. Replace `UserDetailsService` with `AuthenticationProvider` per the v4 auth server design.
- v3 (four-service): most structural changes carry forward, but the JDBC schema, AuthenticationProvider, signing keys, audience enforcement, and header sanitation sections replace their v3 counterparts. See "Corrections From v3" above for the 10 specific changes needed.

If no code has been written for any version, start directly from v4.

## Service Contracts

These endpoints are externally callable through either IAM directly in dev or the gateway proxy.

| Endpoint | Auth | Purpose |
|---|---:|---|

| `POST /api/v1/auth/login` | No | Optional direct login check for diagnostics |
| `POST /api/v1/auth/forgot-password` | No | Request password reset for a specific user type (`userType` in body). Queries only the matching table. |
| `POST /api/v1/auth/reset-password` | No (reset token) | Complete password reset using token from email |
| `GET /api/v1/me` | Any JWT | Get current user's own profile |

| `GET /api/v1/admin/users` | Admin JWT | List all regular users |

| `PUT /api/v1/admin/users/{email}/password` | Admin JWT | Reset a regular user's password |
| `POST /api/v1/admin/users/{email}/disable` | Admin JWT | Disable a regular user account |
| `POST /api/v1/admin/users/{email}/enable` | Admin JWT | Re-enable a regular user account |

### IAM Internal API

The auth server uses this API during OAuth login.

| Endpoint | Auth | Purpose |
|---|---:|---|
| `POST /internal/auth/validate` | Service secret or mTLS | Validate credentials for a specific user type. Body: `{ "email", "password", "userType" }`. IAM queries only the table matching `userType`. Returns principal with `userType` and `authorities`. |
| `GET /internal/users/{email}` | Service secret or mTLS | Load a user from the `users` table by email. Returns single record or 404. |
| `GET /internal/admin-users/{email}` | Service secret or mTLS | Load an admin from the `admin_users` table by email. Returns single record or 404. |
| `POST /internal/auth/revoke-user/{userId}` | Service secret or mTLS | Called by IAM to revoke all tokens for a user. Auth server exposes this endpoint. |

Internal calls must include a service credential, for example:

```http
X-Internal-Token: ${IAM_INTERNAL_TOKEN}
```

Production deployments should replace the shared token with mTLS or a service mesh identity policy.

### Internal Credential Validation Response

```json
// USER response (from users table):
{
  "userId": "123",
  "userType": "USER",
  "email": "alice@example.com",
  "username": "alice",
  "firstName": "Alice",
  "lastName": "Johnson",
  "enabled": true,
  "authorities": []
}

// ADMIN response (from admin_users table):
{
  "userId": "456",
  "userType": "ADMIN",
  "email": "alice@example.com",
  "username": "admin_alice",
  "firstName": "Alice",
  "lastName": "Johnson",
  "enabled": true,
  "authorities": ["ROLE_ADMIN", "ROLE_ADMIN_GROUP_USER_MANAGEMENT"]
}
```

Notes:
- `userType` is the critical field: `USER` means the record came from the `users` table; `ADMIN` means it came from `admin_users`.
- USER records always have an empty `authorities` array. ADMIN records always have at least `ROLE_ADMIN` plus any group-based authorities.
- The same email can appear in both tables — they are distinct accounts.
- `username` is an optional display name. Defaults to the email local-part.
- `firstName` and `lastName` are optional profile fields.
- Do not return `passwordHash` from any IAM API.

### User Model

The IAM server manages two separate account types in two separate tables. Regular users and admin users are distinct entities with different schemas, password policies, and authority models. They are linked only by email — a person may hold one account in each table with the same email address.

All other services reference accounts by their IAM user ID (`sub` claim in JWTs), which must be globally unique across both tables. Use **UUIDs** for both `users.id` and `admin_users.id` to guarantee no collisions across tables:

#### Table: `users` (Regular Users)

```sql
CREATE TABLE users (
    id                     UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    email                  VARCHAR(255) NOT NULL,
    username               VARCHAR(100),
    password_hash          VARCHAR(255) NOT NULL,
    first_name             VARCHAR(100),
    last_name              VARCHAR(100),
    enabled                BOOLEAN NOT NULL DEFAULT true,
    email_verified         BOOLEAN NOT NULL DEFAULT false,
    credentials_changed_at TIMESTAMPTZ NOT NULL DEFAULT now(),
    created_at             TIMESTAMPTZ NOT NULL DEFAULT now(),
    updated_at             TIMESTAMPTZ NOT NULL DEFAULT now(),
    last_login_at          TIMESTAMPTZ,
    CONSTRAINT uq_users_email UNIQUE (lower(email))
);

CREATE INDEX ix_users_username ON users (username) WHERE username IS NOT NULL;
CREATE UNIQUE INDEX ux_users_username ON users (lower(username)) WHERE username IS NOT NULL;
```

#### Table: `admin_users` (Administrators)

```sql
CREATE TABLE admin_users (
    id                     UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    email                  VARCHAR(255) NOT NULL,
    username               VARCHAR(100),
    password_hash          VARCHAR(255) NOT NULL,
    first_name             VARCHAR(100),
    last_name              VARCHAR(100),
    enabled                BOOLEAN NOT NULL DEFAULT true,
    credentials_changed_at TIMESTAMPTZ NOT NULL DEFAULT now(),
    created_at             TIMESTAMPTZ NOT NULL DEFAULT now(),
    updated_at             TIMESTAMPTZ NOT NULL DEFAULT now(),
    last_login_at          TIMESTAMPTZ,
    CONSTRAINT uq_admin_users_email UNIQUE (lower(email))
);

CREATE INDEX ix_admin_users_username ON admin_users (username) WHERE username IS NOT NULL;
CREATE UNIQUE INDEX ux_admin_users_username ON admin_users (lower(username)) WHERE username IS NOT NULL;
```

#### Table: `admin_groups`

Admin users are assigned to groups that determine their specific authorities. Every admin always has the base `ROLE_ADMIN` authority. Groups grant additional fine-grained authorities.

```sql
CREATE TABLE admin_groups (
    id          SERIAL PRIMARY KEY,
    name        VARCHAR(100) NOT NULL UNIQUE,
    description VARCHAR(255)
);

-- Seed groups
INSERT INTO admin_groups (name, description) VALUES
    ('FULL_ACCESS', 'Unrestricted access to all admin functions'),
    ('USER_MANAGEMENT', 'Can manage regular user accounts'),
    ('ADMIN_MANAGEMENT', 'Can manage other admin accounts');
```

Each group maps to a Spring Security authority using the prefix `ROLE_ADMIN_GROUP_`:
- `FULL_ACCESS` → `ROLE_ADMIN_GROUP_FULL_ACCESS`
- `USER_MANAGEMENT` → `ROLE_ADMIN_GROUP_USER_MANAGEMENT`
- `ADMIN_MANAGEMENT` → `ROLE_ADMIN_GROUP_ADMIN_MANAGEMENT`

#### Table: `admin_group_members`

```sql
CREATE TABLE admin_group_members (
    admin_user_id UUID NOT NULL REFERENCES admin_users(id) ON DELETE CASCADE,
    group_id      INTEGER NOT NULL REFERENCES admin_groups(id) ON DELETE CASCADE,
    PRIMARY KEY (admin_user_id, group_id)
);

CREATE INDEX ix_admin_group_members_group_id ON admin_group_members (group_id);
```

#### Key Design Decisions

| Decision | Rationale |
|---|---|
| Separate tables, not a discriminator column | Users and admins will diverge: different password policies, different required fields, different relationships (admin_groups). Separate tables let each evolve independently without nullable columns or check constraints. |
| Same email can exist in both tables | A person can hold a regular user account and an admin account with the same email. They are distinct identities with separate passwords. |
| Admins have no `email_verified` column | Admin accounts are created by other admins, not self-registered. Verification is implicit in the creation process. Can be added later if needed. |
| `admin_groups` with `ROLE_ADMIN_GROUP_` prefix | Distinguishes group-based authorities from the base `ROLE_ADMIN`. Allows method-security expressions like `@PreAuthorize("hasRole('ADMIN_GROUP_USER_MANAGEMENT')")`. |
| Base `ROLE_ADMIN` always granted | Every admin has `ROLE_ADMIN`. Group membership adds additional authorities on top. |

#### Registration

**Regular user registration:**
```
POST /api/v1/auth/register
{ "email": "...", "password": "...", "firstName": "...", "lastName": "..." }
```
Creates a record in the `users` table. `email` must be unique within `users` (409 if already exists). Returns user ID. No authorities granted.

**Admin registration (admin-only):**
```
POST /api/v1/admin/admins
{ "email": "...", "password": "...", "firstName": "...", "lastName": "...", "groupNames": ["USER_MANAGEMENT"] }
```
Creates a record in the `admin_users` table and assigns group memberships. Requires `ROLE_ADMIN` with `ADMIN_MANAGEMENT` or `FULL_ACCESS` group. `email` must be unique within `admin_users` (409 if already exists). Admin password must meet stronger requirements.

#### Login Identifier

Users and admins both log in with their **email address** and password. The login form includes a **user type selector** so the user explicitly chooses which identity they are authenticating as.

Login form fields:
- **Email** — the account email address.
- **Password** — the account password.
- **User type** — a selector (dropdown or toggle) with two options: `User` and `Admin`.

This explicit choice eliminates ambiguity when the same email exists in both tables. An admin who also holds a regular user account can choose "User" to authenticate as their regular identity, or "Admin" to authenticate with their administrative identity.

Authentication flow:
1. User submits email + password + selected user type.
2. IAM queries **only** the table matching the selected type:
   - `User` selected → `SELECT ... FROM users WHERE lower(email) = ?`
   - `Admin` selected → `SELECT ... FROM admin_users WHERE lower(email) = ?`
3. IAM validates the password against the matching record's Argon2id hash.
4. On success:
   - `User` → USER token with `user_type: USER`, no authorities.
   - `Admin` → ADMIN token with `user_type: ADMIN`, `roles` including `ROLE_ADMIN` and group-based authorities, plus scopes.
5. If the email does not exist in the selected table, or the password does not match, return a generic error that does not disclose whether the email exists or in which table.
6. On successful authentication, update `last_login_at` on the matching record.

The internal validation API accepts a `userType` parameter:

```
POST /internal/auth/validate
X-Internal-Token: ...

{ "email": "...", "password": "...", "userType": "USER" }
```

IAM queries only the table indicated by `userType`. The auth server's login form passes the user's selected type through.

The auth server must serve a **custom login page** (not Spring Security's default) that includes the user type selector. This can be a simple Thymeleaf template with an email field, password field, and a dropdown or radio buttons for "User" / "Admin".

#### IAM Signing Keys

The IAM server needs its own signing key pair for password reset tokens. This is separate from the auth server's OAuth2 signing keys.

Requirements:
- A persisted RSA or EC key pair for signing password reset JWTs.
- Local/dev: generate an ephemeral key on startup (acceptable since reset tokens are short-lived and dev restarts are frequent).
- Docker/prod: load from a mounted PEM/PKCS#8 file or secret.
- The public key does not need a JWKS endpoint (only IAM verifies these tokens internally).
- Restarting with the same key keeps outstanding reset tokens valid.

### Password Reset Flow

Users and admins who forget their password can reset it through an email-based JWT token flow. The flow handles both account types — the reset email is sent for whichever table the matching account exists in.

#### Step 1: Request Reset

```
POST /api/v1/auth/forgot-password
Content-Type: application/json

{ "email": "alice@example.com", "userType": "USER" }
```

The `userType` field is required — it tells IAM which table to query. If the user has accounts in both tables, they submit separate forgot-password requests for each type.

Behavior:
- Always return `202 Accepted` with the same response body whether the email exists or not, to prevent user enumeration.
- Query only the table matching `userType` for the email.
- If a matching enabled account is found, generate a password reset JWT and send the reset email. The email body indicates the account type.
- If the email does not exist in that table (or the account is disabled), do nothing but return 202 anyway.
- Rate limit: 1 request per (email, userType) pair per 5 minutes.

#### Password Reset Token

The reset token is a short-lived JWT signed by the IAM server (using its own signing key, separate from the auth server's OAuth2 keys):

| Claim | Value | Notes |
|---|---|---|
| `sub` | User ID | |
| `user_type` | `ADMIN` or `USER` | Identifies which account type this reset is for |
| `purpose` | `"password-reset"` | Restricts token to this single use |
| `jti` | Unique token ID | Enables single-use enforcement |
| `exp` | 15 minutes from issuance | Short window |
| `iat` | Issuance time | |

The token is embedded in a reset link:
```
https://app.example.com/reset-password?token=<jwt>
```

For local development, the link points to `http://localhost:3000/reset-password?token=<jwt>`.

Token storage: persisted in separate tables per account type to enforce single use (DDL shown in User Model section above).

#### Step 2: Complete Reset

```
POST /api/v1/auth/reset-password
Content-Type: application/json

{ "token": "<reset-jwt>", "newPassword": "new-correct-horse-battery-staple" }
```

Validation:
1. Verify JWT signature using IAM's password-reset signing key.
2. Verify `purpose` is `"password-reset"`.
3. Verify token is not expired.
4. Look up `jti` in `password_reset_tokens` — reject if not found or already used.
5. Look up user by `sub` — reject if disabled.
6. Validate new password meets policy (min 8 chars, hashed with Argon2id).
7. Hash new password, update user's `password_hash`, update `credentials_changed_at`.
8. Mark token as used (`used = true`).
9. Revoke all refresh tokens for this user (call auth server `POST /internal/auth/revoke-user/{userId}`).
10. Return `200 OK`.

#### Email Sending

Sending the reset email is required, not deferred. The IAM server must integrate with an email provider:

- Local/dev: Log the reset link to stdout (`logging.level.com.iam.service.PasswordResetService=DEBUG`).
- Docker/prod: Send via SMTP (`spring-boot-starter-mail`) or an external email API (SendGrid, SES, etc.).
- Email template: plain text and HTML, containing the reset link and expiry time.
- Configuration: `EMAIL_ENABLED=true/false`, `EMAIL_FROM`, SMTP host/port/credentials via environment.

## Auth Server Design

### Security Chains

Use two servlet filter chains:

1. Authorization Server chain with `OAuth2AuthorizationServerConfiguration.applyDefaultSecurity(http)`.
2. Application/login chain with form login enabled.

The auth server is not fully stateless. Authorization code flow requires a login session and CSRF protection for login/consent pages. Token endpoints and Authorization Server endpoints use the framework defaults.

### Session State

Authorization code flow requires server-side session state for the login and consent phases.

Session store requirements:

- Local/dev: in-memory sessions are acceptable.
- Shared/prod: use JDBC-backed Spring Session (`spring-session-jdbc`) pointing to the auth server's own `authdb` database, or Redis via `spring-session-data-redis` if Redis is already in the infrastructure. JDBC is the simpler default.
- Sessions must survive an auth server restart. In-progress authorization codes are tied to sessions and will be lost if sessions are in-memory and the server restarts.

Session cookie requirements:

| Attribute | Value | Notes |
|---|---|---|
| `SameSite` | `Lax` | Prevents CSRF on POST but allows top-level GET redirects from OAuth flows |
| `Secure` | `true` | Required in all non-local profiles |
| `HttpOnly` | `true` | Prevents JavaScript access to session cookie |
| Path | `/` | Default |

Session timeout:

- Login session idle timeout: 15 minutes.
- Login session absolute timeout: 1 hour.
- Consent remember-me may extend the absolute timeout per client policy.

Session fixation protection is enabled by default in Spring Security. Do not disable it.

Required behavior:

- `GET /.well-known/openid-configuration` is public.
- `GET /oauth2/jwks` is public.
- `POST /oauth2/token` uses OAuth2 client authentication.
- `GET /oauth2/authorize` redirects unauthenticated users to form login.
- Form login authenticates through `IamAuthenticationProvider` (email + password).

### IAM Authentication Provider

Implement `AuthenticationProvider` for `UsernamePasswordAuthenticationToken`:

1. Receive email, password, and selected user type from Spring Security form login. The login form includes a user type selector (User / Admin).
2. Call `POST ${iam.base-url}/internal/auth/validate` with `{ "email": "...", "password": "...", "userType": "USER" }` or `"userType": "ADMIN"` based on the form selection.
3. Include `X-Internal-Token`.
4. On success, the response includes `userType` and `authorities`. Return an authenticated token with:
   - principal containing `userId`, email, username (display name), firstName, lastName, userType, enabled, authorities.
   - authorities: if `userType = 'ADMIN'` → `ROLE_ADMIN` + `ROLE_ADMIN_GROUP_<name>` per group; if `userType = 'USER'` → no authorities (empty collection).
5. On 401/404/disabled user, throw `BadCredentialsException` or `DisabledException`.
6. Add connection and response timeouts. A down IAM service must fail closed.

Do not implement login with `UserDetailsService.password("{noop}")`.

### IAM Call Resilience

Auth-server calls to IAM are on the login critical path and must fail closed without exhausting servlet threads.

HTTP client requirements:

- Configure connect timeout, response timeout, and connection pool limits.
- Use short default timeouts. Start with 500 ms connect and 2 seconds total response timeout for local/dev, then tune with metrics.
- Treat IAM 401, 403, 404, and disabled-user responses as authentication failures.
- Treat IAM 5xx, timeout, and connection failures as temporary authentication-service failures. Return a generic login failure to the user and log the operational reason internally.
- Do not leak whether an email address exists through error messages.

Retry/circuit-breaker policy:

- Do not retry invalid credentials.
- Allow at most one retry for safe transient failures before user authentication state is created.
- Add a circuit breaker around IAM internal calls.
- When the circuit is open, fail login closed and return a generic authentication unavailable message.
- Expose circuit-breaker state through metrics and health/readiness where appropriate.

Fallback policy:

- No cached password validation.
- No local backdoor admin account in production.
- Optional local emergency admin may exist only in a break-glass profile that is disabled by default and audited.

### Graceful Degradation When IAM Is Unavailable

The auth server has endpoints that depend on IAM (login, authorization) and endpoints that do not (OIDC discovery, JWKS, token introspection of already-issued tokens).

Independence requirements:

- `GET /.well-known/openid-configuration` must return 200 even when IAM is down.
- `GET /oauth2/jwks` must return 200 even when IAM is down. The gateway and resource servers need JWKS to validate existing tokens regardless of IAM status.
- `POST /oauth2/token` with `client_credentials` must work when IAM is down — it does not involve user credentials.
- `POST /oauth2/token` with `authorization_code` or `refresh_token` user tokens may continue to work as long as the authorization/refresh token data in the auth server's own database is valid.
- Only login (form POST to `/login`) and `GET /oauth2/authorize` (which triggers login) require IAM and must fail with a generic "authentication temporarily unavailable" message when the IAM circuit breaker is open.

Health and readiness:

- Auth server liveness must not depend on IAM.
- Auth server readiness may depend on IAM if IAM is on the critical startup path, but should tolerate transient IAM failures after startup.

### OAuth2 Client Storage

Use Spring Authorization Server JDBC repositories:

- `JdbcRegisteredClientRepository`
- `JdbcOAuth2AuthorizationService`
- `JdbcOAuth2AuthorizationConsentService`

The migration must include the official schema for:

- `oauth2_registered_client`
- `oauth2_authorization`
- `oauth2_authorization_consent`

Source the schema from the Spring Authorization Server artifact for the selected version. Do not hand-type a partial table definition.

Seed local clients in `V2__seed_oauth_clients.sql`:

| Client ID | Grants | Scopes | Notes |
|---|---|---|---|
| `web-client` | authorization_code, refresh_token | openid, profile, read, write | Requires PKCE, consent optional by env |
| `service-client` | client_credentials | read, write | Machine-to-machine testing |
| `gateway-client` | client_credentials | internal.gateway | Future internal gateway use |

All `client_secret` values must be BCrypt hashes. Plaintext secrets come from environment or local README examples only.

### OAuth Security Policy

Use OAuth 2.1-style defaults and the OAuth 2.0 Security Best Current Practice posture.

Allowed grants:

- `authorization_code` with PKCE for browser/user login clients.
- `refresh_token` only for clients that use authorization code.
- `client_credentials` only for machine-to-machine clients.

Disallowed grants:

- `implicit`
- `password`
- custom grants until there is a specific reviewed use case

Authorization code client rules:

- Require PKCE with `S256`.
- Require `state` on authorization requests.
- Require `nonce` when `openid` scope is requested.
- Use exact redirect URI matching. No wildcards, no prefix matching, and no dynamic redirect URI registration.
- Allow `http://localhost` redirect URIs only for local development clients.
- Use HTTPS redirect URIs for shared environments and production.
- Prefer public-client behavior for browser/SPA clients. Do not embed long-lived client secrets in browser code.

Refresh-token rules:

- Rotate refresh tokens on every use.
- Set `reuseRefreshTokens(false)` for clients that receive refresh tokens.
- Keep refresh token TTL short enough for the application risk profile. Start with 12 to 24 hours for local/demo, then decide production TTL explicitly.
- Revoke refresh tokens when a user changes password, disables their account, or an admin revokes user access.
- Do not issue refresh tokens for `client_credentials`.

Audience rules:

- Access tokens must include an `aud` claim.
- Gateway and resource-server must validate audience, not only issuer and signature.
- Recommended audiences:
  - `resource-server` for `/api/**`.
  - `iam-api` for `/iam/**` admin APIs.
  - `gateway` only if a token is intended for gateway-specific APIs.
- A token with only `iam-api` audience must not be accepted by the resource-server.
- A token with only `resource-server` audience must not be accepted by IAM admin APIs.

Audience assignment:

- Start with server-side client configuration that maps allowed scopes to allowed audiences.
- For the local `service-client`, issuing `read` or `write` scopes may produce `aud=["resource-server"]`.
- If IAM admin API access is needed, create a separate client or scope that produces `aud=["iam-api"]`.
- Do not let arbitrary request parameters create arbitrary audiences.
- If OAuth 2.0 Resource Indicators are added later, validate every requested resource against the registered client's allowlist.

Client and consent rules:

- Require consent for third-party user-facing clients.
- First-party local clients may disable consent only through an explicit local/dev profile.
- Use exact scope allowlists per client.
- Do not allow clients to request arbitrary scopes.

### Token Claims

Access tokens include:

| Claim | Source | Notes |
|---|---|---|
| `sub` | IAM user ID (UUID) for user tokens, client ID for client credentials | Stable subject; globally unique UUID |
| `jti` | Unique token identifier | Generated by auth server; used for token revocation and audit |
| `email` | IAM email | Primary user identifier; user tokens only |
| `preferred_username` | IAM username (display name) | User tokens only; falls back to email local-part if username not set |
| `given_name` | IAM firstName | User tokens only |
| `family_name` | IAM lastName | User tokens only |
| `client_id` | OAuth2 client ID | Use snake_case standard style |
| `aud` | Requested/allowed resource audience | Required for gateway and resource-server validation |
| `scope` | OAuth2 scopes | Space-delimited string or standard decoded list |
| `user_type` | Account table | `USER` (from `users` table) or `ADMIN` (from `admin_users` table); the critical claim for downstream authorization decisions |
| `roles` | IAM roles | Present **only** for ADMIN tokens. Always includes `ROLE_ADMIN` plus group-based roles like `ROLE_ADMIN_GROUP_USER_MANAGEMENT`. USER tokens have no `roles` claim at all. |

#### Authority Model

The `user_type` claim and source table determine whether a token carries authorities:

| user_type | Source Table | Authorities | Access |
|---|---|---|---|
| `ADMIN` | `admin_users` | `ROLE_ADMIN` + `ROLE_ADMIN_GROUP_<name>` per group membership + `SCOPE_read` + `SCOPE_write` | Full access to admin endpoints (gated by group), resource read/write |
| `USER` | `users` | _none_ (empty) | Authenticated identity only; public endpoints and `/api/me/**` only |

Rules:
- USER tokens contain no `roles` claim, no `SCOPE_*` authorities, and no `ROLE_*` authorities. They represent a pure identity assertion from the `users` table.
- ADMIN tokens always contain `roles: ["ADMIN", "ADMIN_GROUP_<name>", ...]` derived from the `admin_users` table and `admin_group_members`.
- `@PreAuthorize("hasRole('ADMIN')")` gates all admin endpoints. `@PreAuthorize("hasRole('ADMIN_GROUP_USER_MANAGEMENT')")` gates specific admin operations.
- Resource server endpoints requiring `SCOPE_read` or `SCOPE_write` implicitly require ADMIN (USER tokens have no scopes and receive 403).
- The gateway propagates `user_type` via the `X-Authenticated-User-Type` header and roles via `X-Authenticated-Roles`.
- When an admin's group membership is changed, existing access tokens still carry the old group authorities until they expire (bounded by the 5-15 minute token TTL). For immediate revocation, revoke the admin's refresh tokens and let their access tokens expire naturally. Full immediate revocation of access tokens requires a token introspection blacklist (deferred).

For `client_credentials`, do not invent user roles. Use scopes or a separate `client_roles` claim if needed.

### Token Format

Access tokens must use JWS compact serialization (three-part `header.payload.signature`). The `typ` header must be `at+jwt` per RFC 9068.

ID tokens must be issued when the `openid` scope is granted:

| Claim | Source | Notes |
|---|---|---|
| `iss` | Auth server issuer | Must match discovery document |
| `sub` | IAM user ID | Stable subject identifier |
| `aud` | OAuth2 client ID | The client that requested the token |
| `exp` | Token settings | ID tokens should be short-lived, typically 5-15 minutes |
| `iat` | Issuance time | |
| `auth_time` | Last user authentication time | Required by OIDC when `max_age` is used |
| `nonce` | Authorization request nonce | Required when `nonce` was sent in the auth request |
| `preferred_username` | IAM username (display name) | Falls back to email local-part |
| `email` | IAM email | Always included; primary identifier |

ID tokens must be signed with the same key as access tokens unless a separate OIDC signing key is explicitly configured.

### Signing Keys

Create `JwkConfig.kt` with:

- `JWKSource<SecurityContext>` bean.
- `JwtDecoder` bean using `OAuth2AuthorizationServerConfiguration.jwtDecoder(jwkSource)`.
- Local/dev key generation only if no persisted key is configured.
- Docker/prod key loaded from a mounted PEM/JWK file or secret.

Do not generate a new signing key on every restart except in explicit ephemeral dev mode, because old tokens would become invalid.

### Key Rotation Policy

Every signing key must have a stable `kid`.

Key states:

- `active`: used to sign new tokens and exposed in JWKS.
- `previous`: no longer signs new tokens but remains exposed in JWKS until all tokens signed with it expire.
- `retired`: removed from JWKS after the maximum token lifetime plus clock-skew buffer.

Rotation flow:

1. Add new key as `active`.
2. Move the old active key to `previous`.
3. Keep both public keys in `/oauth2/jwks`.
4. Wait at least the maximum access-token lifetime plus accepted clock skew.
5. Remove the previous key from JWKS and delete/archive the private material according to the secret policy.

Implementation requirements:

- JWKS endpoint must expose all active and previous public keys.
- The token header must include the selected key's `kid`.
- Rotation must not require restarting gateway or resource-server.
- A smoke test should issue a token, rotate the signing key, issue a second token, and verify both tokens until the first token expires.
- Document an emergency key revocation procedure for compromised keys. Emergency revocation may invalidate currently issued tokens.

### Token Revocation and Logout

Enable and test Spring Authorization Server revocation support for refresh tokens and client-owned tokens.

Required behavior:

- `POST /oauth2/revoke` revokes refresh tokens and any associated authorization state.
- User password change revokes that user's refresh tokens.
- User disable revokes refresh tokens and prevents new authorization-code login.
- Admin role removal takes effect for new tokens immediately. Existing access tokens remain valid until expiry unless emergency revocation is implemented.
- Logout ends the browser login session. It does not by itself invalidate already-issued access tokens.
- Access tokens should be short-lived so revocation gaps are bounded. Start with 5 to 15 minutes for user tokens and 10 to 30 minutes for service tokens, then tune.

Testing:

- Revoked refresh token cannot be reused.
- Password change prevents refresh-token use and new login with the old password.
- Disabled user cannot log in or refresh.
- Existing access-token behavior after role change is documented and covered by a test if implemented.

### Refresh Token Revocation on IAM State Change

When a user's password changes or their account is disabled in IAM, the auth server must revoke that user's refresh tokens. Since the auth server does not own user state, the following mechanism is used:

**Timestamp-based approach (recommended):**

1. IAM stores a `credentials_changed_at` timestamp on each user record, updated on password change and account disable.
2. IAM's internal validation response includes this timestamp.
3. The auth server stores `credentials_changed_at` in the `oauth2_authorization` row (or a derived column) when issuing refresh tokens.
4. On refresh token use, the auth server calls IAM's `GET /internal/users/{email}` or `GET /internal/admin-users/{email}` (depending on `user_type` in the token) to fetch the current `credentials_changed_at` and compares it against the stored value. If the stored value is older, the refresh token and all sibling tokens for that user are revoked.
5. This adds one IAM call per refresh, which is acceptable given refresh tokens are used infrequently.

**IAM callback approach (used for password reset, admin password change, and account disable):**

1. IAM calls `POST ${auth.base-url}/internal/auth/revoke-user/{userId}` on the auth server with `X-Internal-Token`.
2. The auth server revokes all refresh tokens and active authorizations for that user.
3. This provides immediate revocation for security-sensitive operations.

Use the callback approach for: password reset completion, admin-initiated password change, and account disable/enable. The timestamp-based approach remains the fallback for cases where the callback fails (circuit breaker, network issues).

### Gateway Security

Public through gateway:

- `/actuator/health`
- `/api/public/**`
- `/iam/auth/register`
- `/iam/auth/login`
- `/iam/auth/forgot-password`
- `/iam/auth/reset-password`

Authenticated through gateway:

- `/api/**` except `/api/public/**`
- `/iam/admin/**`
- all other matched routes

Gateway JWT validation config:

```yaml
spring:
  security:
    oauth2:
      resourceserver:
        jwt:
          issuer-uri: ${AUTH_ISSUER:http://localhost:9081}
          jwk-set-uri: ${AUTH_JWKS_URI:http://localhost:9081/oauth2/jwks}
```

In Docker:

```yaml
AUTH_ISSUER: http://localhost:9081
AUTH_JWKS_URI: http://auth-server:9081/oauth2/jwks
```

The issuer is the value inside tokens. The JWKS URI is where the container fetches keys. In production, `AUTH_ISSUER` should be the public HTTPS issuer.

Gateway validation requirements:

- Validate signature through JWKS.
- Validate `iss` against `AUTH_ISSUER`.
- Validate expiry, not-before, and issued-at with a small clock-skew allowance.
- Validate `aud` according to the route:
  - `/api/**` requires `resource-server` audience.
  - `/iam/**` requires `iam-api` audience unless the endpoint is public.
- Reject tokens with missing audience.
- Return 401 for invalid or expired tokens and 403 for authenticated tokens with insufficient authority.

### Header Enrichment

`JwtHeaderEnrichmentFilter` runs after Spring Security has authenticated the request.

Rules:

1. Bypass public paths.
2. Remove inbound `X-User-*`, `X-Client-*`, and `X-Roles` headers before setting new ones.
3. Preserve the `Authorization` header for downstream resource servers.
4. Add convenience headers only:
   - `X-Authenticated-Subject`
   - `X-Authenticated-Client`
   - `X-Authenticated-Scopes`
   - `X-Authenticated-Roles`
   - `X-Authenticated-User-Type`
5. Resource servers must not trust these headers for authorization unless the call also comes through a hardened internal network boundary.

## Resource Server Design

The resource server validates JWTs independently using the same issuer/JWKS split as the gateway.

JWT validation requirements:

- Validate signature through JWKS.
- Validate issuer.
- Validate expiry, not-before, and issued-at with a small clock-skew allowance.
- Validate `aud` contains `resource-server`.
- Reject tokens with only `iam-api`, `gateway`, or unknown audiences.

Authorization rules:

- `/api/public/**`: permit all.
- `/api/me/**`: authenticated (any user type).
- `/api/resources/**`: authenticated with `SCOPE_read` or `SCOPE_write` (ADMIN only; USER tokens have no scopes and receive 403).
- write operations require `SCOPE_write` (ADMIN only).
- read operations require `SCOPE_read` (ADMIN only).
- admin endpoints require `ROLE_ADMIN` (ADMIN only).
- USER tokens can only access `/api/public/**` and `/api/me/**`.
- owner checks compare authenticated subject to resource owner.

Use current Spring Security expressions:

```kotlin
@PreAuthorize("hasAuthority('SCOPE_write')")
@PreAuthorize("hasRole('ADMIN')")
```

Do not use old `#oauth2.hasScope(...)` expressions.

### Authority Mapping

Implement a converter that combines:

- scopes from `scope` or `scp` into `SCOPE_*` (only present on ADMIN tokens).
- roles from a decoded `List<String>` claim into `ROLE_*`. ADMIN tokens have `ROLE_ADMIN` plus `ROLE_ADMIN_GROUP_<name>` per group membership.
- USER tokens have neither claim and receive zero authorities — they can only access permitAll endpoints and `/api/me/**`.
- Admin group authorities: `ADMIN_GROUP_USER_MANAGEMENT` → `ROLE_ADMIN_GROUP_USER_MANAGEMENT`, `ADMIN_GROUP_ADMIN_MANAGEMENT` → `ROLE_ADMIN_GROUP_ADMIN_MANAGEMENT`, `ADMIN_GROUP_FULL_ACCESS` → `ROLE_ADMIN_GROUP_FULL_ACCESS`.

Do not cast roles to `Array<String>`. JSON arrays decode as lists in typical Spring JWT claim handling.

### Backup and Restore

Database backup strategy applies to all three databases:

- **Scheduled backups:** `pg_dump` each database on a schedule appropriate to the data change rate. Daily is a reasonable default.
- **Point-in-time recovery:** Enable WAL archiving in production for PITR.
- **Backup contents:** `authdb` contains OAuth2 clients, active authorizations, and consent records. `iamdb` contains user accounts and role assignments. `resourcedb` contains domain data.
- **Restore test:** A restore test must be run at least quarterly. The restore procedure must be documented.
- **Sensitive data:** Backups contain password hashes and OAuth client secrets. Backup files must be encrypted at rest and access-controlled.
- **Key material:** Signing private keys are NOT in the database. They must be backed up separately through the secret management system.

## Threat Model

This section identifies the primary threats the system must defend against. It is not a full STRIDE/Linddun analysis but establishes the security boundaries that drive design decisions.

### Trust Boundaries

```
[Internet/Client] ---T1--- [Gateway :9080] ---T2--- [Resource Server :9082]
                                |                        |
                               T3                       T3
                                |                        |
                           [Auth Server :9081] ---T4--- [IAM Server :9083]
                                |
                               T5
                                |
                           [PostgreSQL]
```

| Boundary | Description | Protections |
|---|---|---|
| T1 | External client to gateway | TLS, JWT validation, rate limiting, CORS |
| T2 | Gateway to resource/IAM servers | Internal network only; resource servers independently validate JWTs |
| T3 | Gateway to auth server (JWKS fetch) | Internal network; signature-based trust, no shared secrets |
| T4 | Auth server to IAM server | Internal network; `X-Internal-Token` (→ mTLS); circuit breaker |
| T5 | All services to PostgreSQL | Network isolation; per-service credentials; TLS in production |

### Threat Catalog

| Threat | Impact | Mitigation |
|---|---|---|
| Brute-force credential guessing | Account compromise | Rate limiting on login and token endpoints; audit log of failures |
| Token theft (access token) | Impersonation | Short TTL (5-15 min); audience restriction; TLS everywhere |
| Token theft (refresh token) | Long-term impersonation | Rotation on use; revocation on password change; bound to client |
| Forged identity headers | Privilege escalation | Gateway strips inbound `X-Authenticated-*`; resource servers validate JWT, not headers |
| Client secret extraction from SPA | Client impersonation | Public clients for browsers; no long-lived secrets in client-side code |
| Redirect URI manipulation | Authorization code interception | Exact URI matching; PKCE `S256` required |
| Signing key compromise | Unlimited token forgery | Key rotation procedure; emergency revocation; audit log of key operations |
| SQL injection | Data breach | JPA parameterized queries; no raw SQL except Flyway migrations (reviewed) |
| Database credential leak | Data breach | Per-service credentials; credential rotation; no secrets in logs or repo |
| Denial of wallet (token endpoint) | Resource exhaustion | Rate limiting; circuit breaker on IAM calls; connection pool limits |
| Denial of service (IAM down) | Login unavailable | Circuit breaker fails closed; OIDC/JWKS endpoints remain available |
| Replay attacks | Unauthorized access | TLS; short token TTL; nonce in OIDC; state parameter in auth code flow |

### Threat Mitigations by Service

**Gateway:**
- TLS termination at the edge (load balancer or gateway depending on deployment).
- JWT signature, issuer, expiry, and audience validation per route.
- Rate limiting on `/oauth2/token`, `/login`, and `/api/auth/register`.
- Strip forged identity headers; generate or sanitize request IDs.
- CORS allowlist per environment; no wildcard with credentials.

**Auth Server:**
- PKCE `S256` for all authorization code clients.
- Exact redirect URI matching.
- BCrypt OAuth2 client secrets. User passwords are not stored in the auth server.
- Refresh token rotation and revocation.
- Persistent signing keys with key rotation procedure.
- Session cookie: `HttpOnly`, `Secure`, `SameSite=Lax`.
- No secrets in logs.

**IAM Server:**
- Argon2id password hashing.
- Internal API protected by `X-Internal-Token` (→ mTLS).
- No password hashes in API responses.
- Duplicate email detection within the same table (409, not 500). Same email in both `users` and `admin_users` is allowed.
- Audit log of user lifecycle events.

**Resource Server:**
- Independent JWT validation (signature, issuer, expiry, audience).
- `@PreAuthorize` for scope and role checks.
- Owner-based access control.
- Does not trust gateway convenience headers for authorization.

## Security Baseline

Required for implementation:

- Argon2id for user passwords. See Password Hashing below.

### Password Hashing

User passwords must be hashed with **Argon2id**, the winner of the Password Hashing Competition (2015) and the current best-practice algorithm recommended by OWASP.

Argon2id provides three independent dimensions of hardness:

| Parameter | Value | Rationale |
|---|---|---|
| Memory (`m`) | 64 MiB (65,536 KiB) | Resists GPU/ASIC attacks by requiring significant memory |
| Iterations (`t`) | 3 | Three passes over the memory |
| Parallelism (`p`) | 4 | Four threads; typical for server-side hashing |
| Salt length | 16 bytes (128 bits) | Random per-password |
| Output length | 32 bytes (256 bits) | Standard for password verification |

These parameters target approximately 0.5 seconds per hash on current server hardware. Tune at implementation time based on the actual deployment hardware.

Implementation in Kotlin/Java:

Use **Spring Security's `Argon2PasswordEncoder`** (available since Spring Security 5.8):

```kotlin
@Bean
fun passwordEncoder(): PasswordEncoder {
    return Argon2PasswordEncoder.defaultsForSpringSecurity_v5_8()
}
```

The default Spring Security Argon2 encoder uses Argon2id with `m=4096` (4 MiB), `t=3`, `p=1`. For production, override with the stronger parameters:

```kotlin
@Bean
fun passwordEncoder(): PasswordEncoder {
    return Argon2PasswordEncoder(
        16,   // salt length
        32,   // hash length
        4,    // parallelism
        65536, // memory in KiB (64 MiB)
        3     // iterations
    )
}
```

Rules:
- Do not use BCrypt, SCrypt, PBKDF2, or plain SHA-256 for user passwords. Argon2id is the only approved algorithm.
- BCrypt remains acceptable for OAuth2 client secrets (smaller threat surface, client secrets are machine-generated high-entropy values, not human-chosen passwords).
- Every password hash must use a unique random salt (handled automatically by Argon2PasswordEncoder).
- Password minimum length: 8 characters. No maximum (the hash output is fixed-length regardless of input).
- Do not impose character-class requirements (uppercase, digit, symbol). Passphrases and password-manager-generated strings should be equally welcome.

#### Admin Password Policy

Admin accounts have stronger requirements than regular users:

| Parameter | Regular Users | Admin Users |
|---|---|---|
| Argon2id memory (`m`) | 64 MiB (65,536 KiB) | 128 MiB (131,072 KiB) |
| Argon2id iterations (`t`) | 3 | 4 |
| Argon2id parallelism (`p`) | 4 | 4 |
| Minimum password length | 8 characters | 14 characters |
| Maximum password age | None | 90 days (deferred) |
| Password reuse check | None | Last 5 passwords (deferred) |

Implementation:
```kotlin
@Bean
fun adminPasswordEncoder(): PasswordEncoder {
    return Argon2PasswordEncoder(16, 32, 4, 131072, 4)
}
```
Each table uses its own `PasswordEncoder` bean. The encoder parameters are stored in the hash output, so existing passwords continue to validate if parameters change.
- Check new passwords against the Have I Been Pwned k-anonymity API as a deferred feature.
- If Argon2id parameters are changed, existing hashes continue to work (the algorithm and parameters are encoded in the hash output). New passwords use the new parameters. Existing passwords are re-hashed on next successful login (Spring Security's `UserDetailsPasswordService` pattern).

- BCrypt client secrets in the database.
- No default admin password in production profile.
- Authorization-code clients require PKCE `S256`.
- Redirect URIs use exact matching with no wildcards.
- Access tokens include and validators enforce `aud`.
- Refresh tokens rotate and are revoked on password change or account disable.
- Implicit and password grants are disabled.
- CORS allowlist by environment, no wildcard with credentials.

CORS requirements:

- Local/dev: allow `http://localhost:3000` (typical SPA dev server) and `http://localhost:9080`.
- Docker/prod: allow only the specific frontend origin(s) configured per environment.
- Never use `allowed-origins: "*"` when credentials (cookies, Authorization headers) are involved.
- Allowed methods: `GET`, `POST`, `PUT`, `DELETE`, `OPTIONS`.
- Allowed headers: `Authorization`, `Content-Type`, `X-Request-Id`.
- Exposed headers: `X-Request-Id`.
- `Access-Control-Allow-Credentials: true` is required for authorization code flow where the browser sends session cookies to `/oauth2/authorize`.
- CORS configuration should be environment-specific, not hardcoded.

- Rate limiting on login and token endpoints before production.

Rate limiting requirements:

Rate limiting is required, not deferred. Credential-stuffing and token-endpoint abuse are the primary threats to an auth system.

Implementation:

- Gateway-level rate limiting via `RequestRateLimiter` filter or a custom `WebFilter`.
- Token endpoint (`POST /oauth2/token`): limit by client ID (from `Authorization` header) and by source IP. Start with 30 requests per minute per client, 60 per minute per IP.
- Login endpoint (`POST /login`): limit by source IP. Start with 10 requests per minute per IP.
- Registration endpoint (`POST /api/auth/register`): limit by source IP. Start with 5 requests per 10 minutes per IP.
- Forgot-password endpoint (`POST /api/auth/forgot-password`): limit by source IP. Start with 3 requests per 15 minutes per (email, userType) pair.
- Use an in-memory `Bucket4j` or `Resilience4j` rate limiter for local/dev. For shared/prod, back the rate limiter with Redis so limits are consistent across gateway replicas.
- Return `429 Too Many Requests` with a `Retry-After` header when limits are exceeded.
- Do not include rate limit state in the token itself or in client metadata in v1.

- Audit log for login success/failure, password changes, password resets, and admin user changes.
- TLS at the edge in production.
- Persisted signing keys and key rotation plan.
- Production secrets come from an approved secret backend, not repository files.
- Structured logs, metrics, request IDs, and audit events are enabled in shared environments.
- Resource server validates JWTs even when traffic comes through the gateway.

Required for v1:
- Password reset via email JWT link (see Password Reset Flow above).

Deferred but documented:

- Email verification (account activation on registration).
- Email change with verification flow.
- MFA/WebAuthn.
- Dynamic OAuth client registration.
- Service discovery.
- Dynamic gateway routes (new domain services registering at runtime).

```kotlin
companion object {
    @Container
    @JvmStatic
    val postgres = PostgreSQLContainer("postgres:16-alpine")

    @DynamicPropertySource
    @JvmStatic
    fun properties(registry: DynamicPropertyRegistry) {
        registry.add("spring.datasource.url", postgres::getJdbcUrl)
        registry.add("spring.datasource.username", postgres::getUsername)
        registry.add("spring.datasource.password", postgres::getPassword)
    }
}
```

Resource-server tests should use `jwt()` request post processors or construct a valid `JwtAuthenticationToken` through Spring Security test utilities. Do not manually set random servlet request attributes as authentication.

## End-to-End Smoke Test

After `docker compose up --build -d`:

```bash
curl -fsS http://localhost:9081/.well-known/openid-configuration
curl -fsS http://localhost:9081/oauth2/jwks

TOKEN_RESPONSE=$(curl -fsS -X POST http://localhost:9081/oauth2/token \
  -u "service-client:service-secret" \
  -d "grant_type=client_credentials&scope=read")

ACCESS_TOKEN=$(printf "%s" "$TOKEN_RESPONSE" | jq -r .access_token)

curl -fsS http://localhost:9080/api/public/status

curl -fsS -H "Authorization: Bearer $ACCESS_TOKEN" \
  http://localhost:9080/api/whoami

curl -fsS -o /dev/null -w "%{http_code}\n" \
  http://localhost:9080/api/resources
# expected: 401
```

Use `jq` in smoke scripts. Do not parse JSON with `grep`.
